## Context

Applications that deterministically create entities currently attempt an ordinary
create, treat an already-exists error as ambiguous success, reread through a
possibly stale projection, reconstruct defaults and canonical forms, and compare
application-selected fields. That loop is neither linearizable nor portable
across storage backends. A lost create response, a concurrent alternate-key
claimant, or a lagging projection can cause a false match, a duplicate logical
entity, or an unnecessary failure.

Temper already owns the information and serialization points needed to solve the
problem: the canonical IOA write contract, CSDL types and defaults, declared-key
metadata, the authoritative event journal, generated module-data clients, and
Cedar authorization. The missing primitive is one transaction that resolves the
requested identity and every declared key, then either creates the entity or
compares the immutable creation intent that originally won.

Comparing current actor state is incorrect. Caller-owned creation fields may be
mutable after sequence 1, while lifecycle and other host-owned fields were never
part of the caller's creation intent. Query projections are also deliberately
eventually consistent. The durable comparison authority must therefore be a
canonical contract derived from the sequence-1 creation command and co-committed
with that event.

The current declared-key implementation is additions-oriented. The correctness
work in the closed upstream pull request #401 demonstrated that exact ownership
replacement, tombstone/null cleanup, complete-source recovery, and revision
fencing are prerequisites for treating a key lookup as authoritative. This
operation depends on those properties and incorporates them rather than building
a second ownership mechanism.

## Decision

### Add one additive ABI-v1 operation and one distinct capability

`DataOperationV1` gains this additive variant:

```rust
EntityCreateOrVerify {
    entity_type: String,
    idempotency_key: String,
    value: DataObject,
}
```

`DataOperationKind` gains `EntityCreateOrVerify`, serialized in grants as
`entity_create_or_verify`. It is not implied by `entity_create`, and it does not
imply ordinary create or read. Generated entity clients expose:

```rust
pub fn create_or_verify(
    &mut self,
    idempotency_key: impl Into<String>,
    value: &EntityCreate<'_>,
) -> Result<CreateOrVerifyOutcome<Entity>, ModuleDataError>;
```

The same borrowed create command generated by ADR-0195 is reused. The closed
outcome is:

```rust
pub enum CreateOrVerifyOutcome<T> {
    Created { commit: CommitToken, value: T },
    AlreadyMatches { commit: CommitToken, value: T },
    Conflict { fields: Vec<String>, truncated: bool },
}
```

Both successful variants always carry the authoritative canonical entity value
and its per-entity commit token. They never use the ordinary write response's
budget-driven omission form. Before any creation can commit, the host reserves a
conservative encoded response bound using every response-visible property's
effective verified inline ceiling, the maximum permitted returned identity and
sequence, and the larger fixed success envelope. The bound covers later
authoritative state, not only the requested sequence-1 value. If the reservation
does not fit the invocation response budget, the request is rejected with
`ResponseReservationExceeded`. Existing-owner requests use the same pre-lookup
check, preventing budget size from becoming an existence oracle.

The idempotency key is caller supplied, non-empty, and at most 256 UTF-8 bytes.
Its durable scope is `(tenant, logical_module_name, entity_type,
idempotency_key)`. The logical module name, not an artifact or bundle digest,
preserves retries across compatible module publication. The stored mapping binds
the key to the requested creation-contract digest and winning stream identity.
A retry after a committed response loss returns `AlreadyMatches`; reuse with a
different canonical contract returns `Conflict`.

The operation is intentionally excluded from ordinary non-atomic batches and
composite syntax. It adds no OData endpoint and does not change ordinary create.

**Why this approach**: one explicit capability makes both mutation and successful
state disclosure auditable. Reusing the generated create command keeps schema
requiredness, omission, and borrowing identical to ordinary create while a closed
outcome prevents callers from collapsing conflict into transport failure.

### Compile one canonical creation contract from verified metadata

For each verified entity type, the kernel compiles an ordered creation-contract
descriptor from the canonical IOA write contract and its linked CSDL metadata.
The contract includes:

- the entity ID and every property admitted from a caller during create;
- each property's canonical identifier, value source, canonical type descriptor,
  nullability, and canonical default rule;
- a version number and the verified schema/bundle digest;
- a domain-separated SHA-256 hash of each canonical field value; and
- a domain-separated overall digest over the ordered descriptors and field hashes.

Before hashing, the host performs the same create admission and default
materialization used by the authoritative create path. Omitted optional properties
become their declared canonical default or canonical null. Numeric values use the
declared CSDL numeric representation rather than JSON lexical form; enum members
use canonical member identity; entity references use their verified canonical
type and ID; property names and string values follow the schema's existing casing
rules; and absent nullable values become explicit canonical null.

Lifecycle, tenant, module, schema, commit sequence, server-managed properties, and
all other host-owned values are excluded. File content is excluded. The contract
stores no cleartext field value: protected values remain only in the existing
sequence-1 creation event. Contract hashes are never returned, logged, indexed for
queries, or admitted to conflict telemetry.

Field descriptors are sorted by canonical schema identifier before hashing and
persisting. Canonical binary framing is length-prefixed and type-tagged; it never
depends on JSON object order, map iteration, locale, wall time, or randomness.

**Why this approach**: the original default-materialized create command is the
immutable intent that retries must verify. Per-field hashes permit bounded
diagnosis without duplicating protected values, while an overall digest supplies a
cheap equality and idempotency key.

### Compare contracts across compatible schema evolution

The persisted contract is versioned independently of the application-data ABI.
When stored and target schema digests differ, comparison constructs a deterministic
view under the target schema:

- common properties compare only when canonical type and value source are
  identical;
- removed properties are dropped from comparison;
- a newly added optional property is synthesized from the target default or null
  rule for the historical contract;
- a newly added required property, or an incompatible type/value-source change,
  fails with `CreationContractMigrationRequired`; and
- a changed default/null rule for a common property is a descriptor mismatch and
  therefore a `Conflict`, as is any changed canonical value.

Contract migration never reads later mutable state. Where an old creation event
must be materialized, only sequence 1 and the exact verified schema contract that
governed it may be used. Scoped streams always use their durable pinned bundle.

Global streams created before this feature are baselined once under the current
verified schema. A per-`(tenant, entity_type)` coverage watermark stores the exact
contract revision and declared-key signature. It is published only after every
sequence-1 event and every ownership source for the type has been reconciled with
no unresolved duplicate, missing schema, decode error, or source race. Until then,
create-or-verify fails closed for a potentially legacy owner rather than guessing
from mutable state.

**Why this approach**: optional additive evolution can retain the meaning of an
old create without weakening requiredness. Incompatible evolution is surfaced as
an explicit migration obligation instead of silently converting mismatches into
success.

### Resolve identity and all declared keys inside one store transaction

`EventStore` gains a typed `create_or_verify` transaction contract. Its input
contains the requested tenant/module/type/ID, expected-empty stream coordinates,
the canonical sequence-1 event and creation contract, the exact declared-key rows,
the idempotency binding, and the contract/key revision. Its result is one of:

- `Created`, with the committed stream identity and sequence;
- `Existing`, with the winning stream identity, sequence-1 contract, and
  idempotency disposition; or
- a typed deterministic multi-owner, tombstone, migration, or storage conflict.

Within the transaction the store:

1. validates or reserves the scoped idempotency record;
2. resolves the requested stream and every declared-key owner;
3. validates coverage, contract revision, and all creation fingerprints;
4. deterministically selects the single owner when identity and keys agree; and
5. either commits the first event, creation contract, exact key set, catalog row,
   and idempotency mapping together, or returns the typed existing result without
   mutation.

Identity is a declared owner in this resolution set. A matching alternate-key
owner may produce `AlreadyMatches` even when its entity ID differs from the
requested ID; only the successful commit token reveals that actual identity.
When identity and one or more keys resolve to different owners, the operation
returns a deterministic conflict and never chooses by lookup timing.

Tombstoned requested identities return `Conflict` containing the canonical
lifecycle property identifier. Non-identity keys released by a durable delete or
null transition may be claimed by another entity. A tombstone never releases its
identity.

Every creation path—entity actor, native data-only fast path, composite sub-create,
trigger, scoped bootstrap, module-data create, and OData create—must supply and
co-commit the creation contract. There is one helper for contract construction and
one exact declared-key reconciliation contract. No path may append sequence 1 and
repair metadata afterward.

After `Created` or `Existing` comparison succeeds, the server loads the
authoritative actor through at least the returned sequence and returns that
canonical state. A later actor sequence is valid. Query projections are never
consulted. Before returning `AlreadyMatches`, the server revalidates that the
loaded stream identity and preserved contract still match the transaction result;
no success may mask mismatching authoritative state.

**Why this approach**: stream identity, business-key identity, retry identity, and
the sequence-1 comparison authority form one serialization problem. Splitting any
of them into a preflight query or post-commit repair reintroduces the ambiguity the
operation exists to remove.

### Declared keys have exact-set ownership and revision fencing

All durable writes replace an entity's declared-key ownership with the exact set
derived from the newly committed state. Empty, null, changed, and deleted keys
remove prior non-identity rows in the same transaction. Composite, native
data-only, trigger, bootstrap, actor, and OData writes use this same primitive.

Backfill enumerates the union of catalog, journal, snapshot, field-index, and
key-only owners so deleted, orphaned, and partially materialized streams cannot be
skipped. It records the sequence/source coordinates used to derive each repair and
rechecks them before commit. Coverage is fenced by a versioned signature over key
names, ordered canonical property/type descriptors, lifecycle semantics, and the
creation-contract revision—not only key names. A changed signature invalidates
coverage and forces exact reconciliation. Duplicate ownership or incomplete
authoritative materialization leaves coverage unpublished.

These rules incorporate the relevant correctness findings from closed upstream
PR #401 without importing its unrelated changes.

### Authorization precedes ownership lookup and explicitly permits disclosure

The host first validates the request and capability, materializes the requested
canonical create fields, reserves the response budget, and authorizes Cedar action
`create_or_verify` against those requested fields. Only then may it resolve an
identity, key owner, idempotency record, tombstone, or creation contract.

Authorization denial is identical for absent and present entities. The distinct
permit explicitly authorizes disclosure of successful canonical state, including
the actual identity of a matching alternate-key owner. `entity_create`,
`entity_get`, or broad read permission is insufficient by itself.

Conflict disclosure contains only canonical schema-owned field identifiers. It
never contains existing values, requested values, hashes, owner IDs, or protected
host fields other than the lifecycle identifier for the specified tombstone case.
Identifiers are sorted canonically, duplicates removed, and consumed from a
32-field disclosure budget. `truncated` is true whenever another differing or
ownership-identifying field exists after the budget is exhausted. The same bounded
identifiers are safe for redacted telemetry.

**Why this approach**: authorization on requested fields preserves create policy,
while the new permit makes alternate-owner disclosure intentional. Pre-lookup
ordering and uniform denial prevent the operation from becoming an existence
oracle.

### Backend transactions have one observable contract

- **Sim** holds one mutex across idempotency, owner resolution, contract comparison,
  exact-key reconciliation, first-event append, and catalog mutation. Named,
  deterministic fault points exist before commit, after commit/before reply, and
  around authoritative load; schedule controls never use wall time or threads.
- **PostgreSQL** stores versioned contracts and idempotency mappings in tenant-
  scoped tables. It acquires advisory/row locks in deterministic order by type,
  canonical key coordinates, then stream identity; the journal, contract, exact key
  set, catalog, and idempotency mapping commit in one SQL transaction.
- **Turso** uses an immediate serialized transaction for the same rows and maintains
  declared keys live. Contract/key backfill is bounded, resumable, revision-fenced,
  and publishes coverage only after a complete pass.
- **Redis** uses one Lua script whose tenant-scoped keys cover stream identity,
  declared-key owners, contract, idempotency mapping, catalog, and first-event
  append. Existing tenant hash-tag/scoping conventions are preserved so every key
  participating in the script shares a slot.

Backend implementations return the same typed dispositions and use the same
canonical contract bytes. Backend-specific uniqueness errors do not escape as
public semantics.

## Rollout Plan

1. Land the complete storage schema, exact-key reconciliation, contract compiler,
   backend implementations, backfill, ABI/SDK surface, authorization, telemetry,
   and parity/DST tests with the new grant disabled by default.
2. Deploy and run the bounded contract/key reconciliation. Observe per-type
   progress and failures; publish coverage only for completely reconciled types.
3. Enable `entity_create_or_verify` grants and the Cedar action for selected
   modules after their types report exact coverage. Exercise identical retry,
   divergent binding, lost response, restart, and stale-projection cases live.
4. Adopt the generated operation in TemperPaw through a separate PR, beginning
   with `ensure_inference_candidate` in `simulate_arc_submission`, then broaden use
   only after live telemetry confirms convergence.

## Consequences

### Durable Created observation

The durable sequence-one journal event is the replay source for every public
entity SSE surface. Handlers subscribe before reading history, replay tenant- or
entity-filtered journal events, and suppress live duplicates through per-entity
high-water sequences. Scoped journals resolve their encoded storage coordinate
to the public entity ID from immutable sequence-one parameters. Tenant-wide
replay is paged and fails closed when its explicit event budget is exhausted.
The notification reservation is acknowledged only after process-local publish;
disconnect, lag, or restart remains recoverable from the journal independently
of that acknowledgement.

### Overflow blob/catalog crash ordering

Create-or-verify commits the sequence-one event and its catalog/query projection
before writing immutable, content-addressed overflow objects. The event retains
the full canonical creation parameters, so a crash or partial object-store
failure is recoverable: retry and authoritative replay regenerate the same object
keys and bytes idempotently. Successful disclosure remains gated on completion of
every referenced object write. This ordering prevents failed or conflicting
pre-commit attempts from leaving permanent unreferenced objects; a transiently
missing object after commit is repaired from the durable journal rather than
guessed from a projection.

### Positive

- Deterministic creation becomes linearizable and retry-safe without projection
  polling or application-specific compare loops.
- Identity and alternate keys share one ownership decision across every backend.
- Successful results are authoritative, typed, commit-bearing, and explicitly
  authorized.
- Schema-compatible historical contracts remain usable without comparing mutable
  state.

### Negative

- Every creation path gains synchronous contract and exact-key write
  amplification.
- Existing global streams require a complete, fail-closed baseline before this
  operation can safely run for their type.
- An additive optional property can be synthesized, but required or type/source
  changes need an explicit creation-contract migration.

### Risks

- Incomplete owner enumeration could publish a false coverage watermark. The union
  of durable sources, source-coordinate rechecks, revision fencing, and
  fail-closed publication mitigate this.
- Canonicalization drift could split identical requests. One shared compiler and
  persisted versioned descriptors are used by every backend and backfill.
- Authorization ordering could leak existence. Capability, validation, response
  reservation, and Cedar authorization are completed before any lookup, with
  uniform denial tests.
- A committed operation could lose its reply. Durable scoped idempotency makes the
  retry return `AlreadyMatches` without a second append.
- A fresh PostgreSQL fork database could fail its first restart if the lineage
  classifier omitted a published fork migration. Fork migrations 12 through 14
  are therefore treated as one immutable pre-shared prefix and restart-tested.
  Shared migration 19 also idempotently converges the fork-only migration 14
  bootstrap tables and policies onto the legacy and fixed-upstream lineages.

### DST Compliance

- Creation-contract bytes use ordered descriptors, length-prefixed canonical
  framing, SHA-256, `BTreeMap`/`BTreeSet`, and no time or randomness.
- Sim executes the transaction under one mutex and exposes deterministic named
  fault/interleaving points.
- Seeded schedules cover identical and divergent writers, commit/reply loss,
  restart, backfill races, and stale projections.
- No simulation-visible path uses wall clock, filesystem/network I/O, random UUIDs,
  multi-thread spawning, or unordered collections.

## Non-Goals

- General upsert, merge, repair, patch, or caller-supplied predicates.
- Changing ordinary create semantics or adding create-or-verify to ordinary batch.
- An OData endpoint or new IOA syntax.
- Comparing later mutable workflow state.
- Returning conflicting values, hashes, or owner identity.
- File content or blob put-or-match semantics.
- Application-specific ARC/provenance logic in the Temper kernel.

## Alternatives Considered

1. **Create, catch conflict, then query and compare** — rejected because projection
   lag and concurrent key claims make the result non-linearizable.
2. **Compare current authoritative actor state** — rejected because mutable fields
   no longer represent the original creation intent.
3. **Reuse ordinary create or read permission** — rejected because successful
   alternate-owner state is a distinct disclosure requiring explicit authority.
4. **Store the complete canonical creation object separately** — rejected because
   it duplicates protected values already present in the creation event.
5. **Add IOA comparison syntax or caller predicates** — rejected because existing
   verified write/default/type/provenance metadata completely defines the contract
   and arbitrary predicates would turn the primitive into upsert.
6. **Treat alternate-key ownership as conflict when IDs differ** — rejected because
   declared business keys establish logical ownership; a canonically matching owner
   is the entity the deterministic create intended to ensure.

## Rollback Policy

Disable the `entity_create_or_verify` grant and Cedar action to stop all new use.
The additive ABI decoder and derived contract/idempotency rows remain readable;
they are not dropped or rewritten during rollback. Ordinary create and all existing
read/write operations continue unchanged. Exact declared-key reconciliation remains
enabled because it repairs an independent correctness defect. A later deployment
may re-enable the action without re-baselining already covered contract revisions.
